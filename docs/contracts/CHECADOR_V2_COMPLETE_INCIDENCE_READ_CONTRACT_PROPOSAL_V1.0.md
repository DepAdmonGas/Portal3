# Checador V2 — Complete Incidence Read Contract Proposal V1.0

**Status:** `DRAFT_NOT_APPROVED`
**Implementation authorized:** `NO`
**Purpose:** specify the read coverage needed to preserve Portal3's complete incidence workspace; this document does not authorize implementation, a new endpoint, direct SQL, or a schema change.

## 1. Decision boundary

The Architecture Freeze V1.0 is frozen and does not authorize implementation. The frozen P3G administrative contract establishes the canonical V2 incidence domain and prohibits Portal3 from constructing a competing incidence authority. P3G-A status evidence records a verified development read path through existing API endpoints: `GET /api/v2/incidences` for applicable summaries, `GET /api/v2/incidences/{uuid_incidencia}` for a single incidence and complete append-only revision history, and `GET /api/v2/administrative-evaluations` for an existing evaluation or a neutral no-evaluation result. Those API calls are server-to-server behind the authenticated Portal3 boundary.

The observed `ChecadorPersistedIncidenceReadService::getPersistedIncidences()` is a broader, direct-MariaDB read. It queries a workplace-wide date-overlap list and enriches each item with current revision, applications, linked schedule/shift, administrative evaluations, worker/date punches, and revision history. This is observed code, not evidence that direct SQL is an approved alternate source or that the P3G-A API contract is equivalent to the complete workspace. The P3G contract's governance freeze says implementation is not authorized; P3G-A verified development status is implementation evidence within its selected canonical worker/workplace/date read boundary, not blanket approval for this broader list.

M06 authorizes a narrowly defined PUNCH_ATTENDANCE check association/deadline and does not broaden collection reads. P3G-B authorizes development writes for create/revision and readback of those records/history; it does not authorize broad listing, lifecycle changes, or evaluation. Neither addendum fills the complete-read gaps below.

## 2. Current Portal3 behavior observed

- Inputs: workplace ID, inclusive `dateFrom`/`dateTo`, optional worker ID, incidence type and status. Invalid workplace/date returns an error; reversed dates are swapped; a range longer than 93 days is truncated from its start date.
- List selection: workplace-scoped incidence master whose date interval overlaps the requested interval (`start <= requested end` and `end >= requested start`); optional worker/type/current-status filters. Ordering is start date descending, worker name ascending, master ID descending. The service fetches all matched rows; no pagination, cursor, separate count, or source-completeness marker is implemented.
- Identity/context: master ID and UUID, worker ID/name/employee number, workplace/locality ID/name, category/type, incidence scope, local date interval, current state/revision, current reason/evidence reference, creator/approver IDs and UTC creation/update timestamps.
- Revision/application enrichment: full ordered revision history; revision number/status/reason/evidence/creator/approver/time; applications of the current revision; scheduled-workday references and application status; associated shift/template and formatted hours; evaluation records linked through those applications.
- Punch enrichment: raw punch records for the worker over the min/max incidence dates, associated by local date interval. The current method converts interval boundaries to UTC with a hard-coded `America/Mexico_City` timezone. This association must not be represented as an API-owned exact event link unless API source/reference confirms that relation.
- Time display: shift times use the schedule timezone with current fallback behavior; master creation display converts UTC using `America/Mexico_City`. These are observed presentation rules, not proof that the timezone is authoritative for every workplace/date.
- Empty/error state: empty SQL list returns `ok:true`, no incidence rows and `total:0`; invalid input returns safe error keys. SQL exceptions return exception text. A future contract must distinguish verified empty results from partial/unavailable source and use safe errors.
- Authorization: controller requires authenticated user, workplace-scope authorization and `authorizeIncidenceRead(workplace)`. The raw SQL service itself accepts only IDs/filters, not authenticated identity. Under the existing API read path, Portal3 restricts lookups to canonical worker/workplace/date, while API must revalidate caller permission and canonical scope. Browser-supplied workplace/worker values do not themselves prove scope.

## 4. Existing endpoints that can be reused

The existing endpoints should be reused only for their demonstrated equivalent portions:

1. `GET /api/v2/incidences` — P3G-A applicable summaries for the selected canonical worker, workplace and date range. Current Portal3 validates returned worker/workplace/range and summary count. It is not demonstrated as a complete workplace-wide collection endpoint with type/status filters, pagination, and all enrichments.
2. `GET /api/v2/incidences/{uuid_incidencia}` — complete append-only revision history for one incidence. Reuse this for history after a valid summary UUID; cross-resource completeness/partial behavior for a list remains to be specified.
3. `GET /api/v2/administrative-evaluations` — existing evaluation or neutral no-evaluation for one worker/workplace/work date. It does not by itself provide all evaluations across every linked application/date in the current broad listing.
4. `GET /api/v2/punch-events` — raw observations under M05's permission, workplace scope, pagination and completeness rules. It is not a generic incidence-to-event link. M06 `check_reference` applies only to its defined PUNCH_ATTENDANCE case.

No endpoint for the required complete workplace-wide incidence projection is declared here. Whether to extend a frozen endpoint or approve a new API read boundary is a decision for the API/architecture owners; method, route, ACL and schema remain unspecified until that decision is approved.

## 5. Proposed logical contract (not an endpoint declaration)

Define an API-owned read projection sufficient to query all incidences in an authorized workplace/date interval with the current Portal3 filters and details. Specify whether the operation returns a complete projection or a paginated list whose detail resources are independently fetched. Cover stable source order, completeness across pages and child reads, summary/detail identifiers, revision history, application references/status, schedule/shift reference, evaluation references, exact PunchEvent/check links when authorized, provenance, effective workplace timezone, safe errors and neutral empty/no-evaluation states.

The contract must preserve the canonical V2 incidence domain and append-only revision authority; it must not add Portal3 SQL reads, duplicate storage, infer application outcomes, invoke evaluation, or broaden P3G/M06/P3G-B permissions. HTTP method, route, query schema, response field names, ACL identifier and paging strategy are `TBD_BY_API_CONTRACT_OWNER`.

## 6. Approvals required before implementation

1. **Architecture/API:** decide whether the current complete workplace read is within the frozen P3G boundary. If not, approve the necessary shared contract amendment before route, payload, ACL, schema or runtime changes. Preserve Architecture Freeze unless a formally approved amendment is issued.
2. **API owner:** approve list scope, date overlap, type/status filters, pagination/completeness, application and schedule references, linked evaluations, exact punch/check links, revision detail behavior, timezone semantics, stable error/partial envelopes and API-side authorization.
3. **Portal3 owner:** approve the corresponding read capability, authenticated user to canonical locality mapping, UI behavior for partial/unavailable data and no-result states, and how current modal data remains equivalent.
4. **Lector:** shared approval is required if the API change alters a common incidence/evaluation resource or Lector consumes the added projection; otherwise no Lector integration is proposed.
5. **Business/J2 or schedule owner:** approve any schedule/effective-version and timezone-derived display values that are not already available under an approved schedule contract.

P3G-B development write/readback and M06's scoped check association do not satisfy these approvals. This proposal authorizes no implementation, SQL, migration, ACL grant, new endpoint, write, production gate, or deployment.
